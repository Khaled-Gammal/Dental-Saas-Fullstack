# مراجعة R11 — ملخص التغييرات

Oct 31, 2026 · @Bronto24 Academy

## نظرة عامة

خلصت مراجعة R11 كلها في 7 دفعات: الموقع والـ API والداشبورد وقاعدة البيانات. أضافت 19 migration جديد (من 44 لـ 62)، ومفيش migration قديم اتعدل.

المراجعة اتعملت بقراءة الكود، واتأكدنا من أخطر النتايج مباشرة في الملفات. اتشغّلت كل الـ migrations وكل تستات الـ SQL على PostgreSQL 16 محلي بعد كل دفعة، وكلها عدّت، وجرّبنا الـ down وبعده الـ up تاني. تستات الـ API والداشبورد (e2e و unit) اتشغّلت على جهاز التطوير بعد كل دفعة وعدّت.

التعليقات في الكود الجديد عليها علامة `review R11`، عشان سبب أي تغيير يبقى سهل تلاقيه.

## الخطوة 1: الإصلاحات الحرجة

أول دفعة قفلت 6 ثغرات كان يقدر يستغلها أي مستخدم حقيقي، من غير ما يحتاج SQL injection.

| المشكلة | الإصلاح | فين |
| --- | --- | --- |
| مدير محدد له فروع كان يقدر يدي نفسه "كل الفروع" | مبقاش يقدر يعدّل فروعه، ولا يعدّل موظفين في فروع تانية، ولا يدي فرع مش بتاعه (في التعديل والدعوة) | `staff.service.ts` |
| الحجز من الموقع كان بيكتب إيميل جديد فوق إيميل مريض موجود | الإيميل المسجل بيفضل زي ما هو، والملف بيتعلّم "يحتاج مراجعة" والإيميل الجديد بيتسجل في سجل النشاط | `patient-directory.ts` |
| سر الـ revalidate كان بيدخل في bundles الموقع بقيمة معروفة | بيتقرا وقت التشغيل بس، والـ endpoint بيرجع 503 لو السر ناقص أو قيمة تطوير في الـ production | `next.config.ts`، `revalidate/route.ts` |
| رد الحجز العام كان فيه اسم المريض ورقمه ورقم ملفه والملاحظات الداخلية | بقى فيه الدكتور والخدمة والفرع بس | `book-online.usecase.ts` |
| الضغط مرتين على الاسترداد أو الإعفاء كان بيسجّله مرتين | نافذة التأكيد بتقفل الزر وهو بيشتغل، والاسترداد بقى بـ idempotency key | `confirm-dialog.tsx`، migration 45 |
| إجراء مريض كان ممكن يتفوتر على فاتورة مريض تاني | trigger في الداتابيز بيمنعه، وشاشة الفاتورة بتختار إجراءات فرع الفاتورة بس وبتظهر الفرع | migration 44، `billing/new.tsx` |

في نفس الدفعة اتشال باكدج `cn` (باكدج خارجي مش مراجَع، وكانت 13 ملف بتستخدمه بدل `@/lib/utils`)، والمطلوب كمان مسح `api-test.txt` من جذر المشروع.

## الخطوة 2: تقوية قاعدة البيانات

لو ظهر SQL injection في أي حتة في الـ API، مبقاش يقدر يعطّل الحمايات أو يمسح بيانات مالية أو طبية. ده اتعمل في migrations 46–48.

- **مفتاح تعطيل الحمايات (`app.allow_hard_delete`):** مبقاش بيشتغل غير لاتصال داخل بـ role بيتخطى RLS (الـ worker أو superuser)، وعمره ما بيشتغل لـ `app_user`. الـ 11 دالة اللي كانوا بيقروه مباشرة بقوا يسألوا `hard_delete_allowed()`.
- **صلاحية الحذف:** `app_user` بقى يمسح من 15 جدول بس (المسودات والمواعيد الأسبوعية والروابط). العيادات والمدفوعات والزيارات والمرضى والمواعيد الحذف فيها مرفوض من الصلاحيات نفسها، ومبقاش يقدر يعدّل الدومينات.
- **`search_path`:** كل دوال `SECURITY DEFINER` بقى الـ search\_path بتاعها `public, pg_temp`، فمحدش يقدر يغطّي عليها بجدول مؤقت.
- **جداول من غير RLS:** `webhook_events` اتقفل على الـ API، وعمودي الـ IP والمتصفح في `legal_acceptances` بقوا مخفيين.

**قاعدة جديدة:** أي جدول جديد `app_user` مش بياخد عليه DELETE تلقائيًا. لو الـ API محتاج يمسح منه، الـ migration بتاعه لازم يعمل `GRANT DELETE` صريح.

الدفعة دي صلحت 9 مشاكل في السلوك: رسايل كانت بتضيع أو بتتبعت غلط، وجلسات كانت بتفضل شغالة، وشاشات كانت بتعرض بيانات قديمة.

| المنطقة | المشكلة | الإصلاح |
| --- | --- | --- |
| الإشعارات | نقل الميعاد لوقت اتستخدم قبل كده كان بيضيّع التذكيرات | المفتاح بقى مربوط بعملية النقل (الـ outbox event) مش بالوقت |
| الإشعارات | العيادة المحذوفة كانت لسه بتبعت إيميلات في فترة الـ 90 يوم | رسايلها بتتلغي زي العيادة الموقوفة |
| الإشعارات | إشعار وقع الـ worker في محاولته الخامسة كان بيفضل `queued` للأبد | بيتحول `failed` بعد المهلة وبيتسجل error |

| الكاش | شاشة الزيارة كانت بتعرض الحساسية القديمة بعد تعديل التاريخ المرضي | تعديل التاريخ المرضي بيحدّث الشاشات الطبية |
| الكاش | الدمج كان بيسيب الرصيد والمواعيد القديمة | بيحدّث المريض والفواتير والمواعيد والزيارات |
| الكاش | بعد إنهاء الميعاد الزيارة كانت بتفضل قابلة للتعديل والحفظ يفشل | أي حاجة بتحصل للميعاد بتحدّث الزيارات وملف المريض |

## الخطوة 4: الـ indexes والأداء

ضفنا 8 indexes، كلهم `CONCURRENTLY` وكل واحد في ملف لوحده عشان ميقفلوش الجداول، وصلحنا 3 استعلامات كانت تكلفتها بتكبر مع عمر العيادة مش مع الطلب.

- **مواعيد العيادة بالوقت:** index على `appointments(tenant_id, starts_at)`، لعرض كل الفروع والتقارير وأرقام الصفحة الرئيسية.
- **حذف خدمة:** index على `service_id` في المواعيد والإجراءات وبنود الفواتير وبنود خطط العلاج، بدل ما كان بيعدّي على الجداول دي كلها.
- **دمج المرضى:** index على `notifications.patient_id`.
- **البحث بالموبايل:** indexes على `phone_alt` و `guardian_phone`، واتأكدنا من خطة التنفيذ على 30 ألف مريض إنه بقى يستخدم التلاتة مع بعض (BitmapOr).
- **تقرير المرضى الجدد (migration 58):** بقى يقرا زيارات الفترة بس بدل تاريخ العيادة كله. النتيجة مطابقة للقديم على 759 زيارة عشوائية في 280 فترة.
- **تصدير بيانات العيادة:** بيقرا بـ cursor جوه الـ snapshot بدل `LIMIT/OFFSET` اللي كان بيرتّب الجدول كله مع كل صفحة.
- **رفع الصور:** الصورة بتتفك مرة واحدة بدل مرة لكل مقاس (كانت 3 مرات).

## الخطوة 5: التنظيف والتوقيت

الداشبورد بقى يعرض كل التواريخ بتوقيت العيادة من مصدر واحد، واتشالت كذا حاجة مكررة أو مش مستخدمة.

**التوقيت:**

- `Africa/Cairo` كان مكتوب في حوالي 28 مكان. دلوقتي فيه `clinicTimeZone()` في `util.ts`، وبياخد المنطقة من ملف العيادة (`/clinic/profile` بقى يرجّع `timezone`).
- 9 نسخ من دالة "تاريخ النهارده" بساعة المتصفح بقوا `clinicToday()`، و 12 نسخة من ثابت اللغة بقوا `LOC`.
- نهاية الفترة التجريبية كانت `+02:00` ثابتة، فكانت بتنتهي ساعة متأخر في التوقيت الصيفي. دلوقتي بتتحسب صح.
- "مفتوح الآن" في الموقع بيتحسب في المتصفح وبيتحدث كل دقيقة (`live-status.tsx`)، فأول زائر الصبح مبقاش بيشوف "مغلق" من نسخة الليل.

**حاجات صغيرة:**

- حد الـ JSON في الـ API بقى 1MB، لأن الوثائق القانونية فوق 50 ألف حرف كانت بترجع 413.
- معالج الحجز مبقاش بيلغي الدكتور المختار لما تغيّر الخدمة أو الفرع، طالما بيقدّمها هناك.
- الموقع بقى بيبعت security headers: HSTS (بدون includeSubDomains) و `nosniff` و `X-Frame-Options` و `Referrer-Policy` و `Permissions-Policy`.
- `tailwindcss` و `@tailwindcss/vite` اتنقلوا لـ devDependencies.

**تنظيف الداتابيز (migrations 59–61):** اتشال index مكرر على `installments`، و index على `legal_acceptances(user_id)` لأن الـ unique index بيغطيه، ودالتين `SECURITY DEFINER` محدش بيستخدمهم (`invitation_by_token` و `tenant_for_payment`).

## role لوحة المنصة و pepper الباسوردات

التغييرين دول بيقفلوا آخر طريقين كان SQL injection ممكن يستغلهم: دوال المنصة، و hashes الباسوردات.

### role منفصل للوحة المنصة (migration 62)

- دوال `platform_*` بتصدّق أي `p_actor` يتبعتلها. قبل كده كان `app_user` يقدر يشغّلها، فأي injection في كود العيادات كان يقدر يوقف عيادات بـ id أدمن.
- دلوقتي `app_platform` بس هو اللي بيشغّلها (ما عدا `expire_trials` اللي للـ worker)، وهو بس اللي بيقرا سجل المنصة. وممنوع عليه أي بيانات عيادات أو password hashes.
- الـ API بقى فيه connection تاني (`PLATFORM_DB`) بيستخدمه `PlatformRepository` بس، ومتغير جديد `DATABASE_PLATFORM_URL`. اسم الداتابيز بيتاخد دايمًا من `DATABASE_URL`.

### pepper للباسوردات

- قبل scrypt، الباسورد بيعدّي على HMAC-SHA256 بمفتاح `PASSWORD_PEPPER` اللي موجود في إعدادات السيرفر بس. لو جدول `users` اتسرّب، مش هينفع حد يخمّن الباسوردات offline.
- الصيغة الجديدة `pscrypt$…`، والقديمة `scrypt$…` لسه بتشتغل. أول ما أي يوزر يسجّل دخول صح، الـ hash بتاعه بيتحول لوحده.
- **تحذير:** `PASSWORD_PEPPER` بيتحط مرة واحدة لكل بيئة ومبيتغيرش. لو اتغير، كل اليوزرز اللي اتحولوا مش هيقدروا يدخلوا لحد ما يعملوا reset.

## قبل النشر على الـ production

أول ثلاث خطوات لازم تتعمل قبل `db:migrate` وقبل ما الـ API يشتغل، وإلا الـ API هيرفض يشتغل أو اللوحة هتقع.

- [ ] إنشاء role `app_platform` بـ `LOGIN` وباسورد قوي و `NOSUPERUSER NOBYPASSRLS`، وإضافة `DATABASE_PLATFORM_URL`
- [ ] ضبط `PASSWORD_PEPPER` لقيمة عشوائية طولها 48 حرف أو أكتر، وحفظها في مكان آمن
- [ ] ضبط `REVALIDATE_SECRET` لقيمة حقيقية في الـ API والموقع، لأن الـ endpoint بيرجع 503 من غيرها
- [ ] تشغيل `pnpm install` وعمل commit للـ lockfile الجديد (شيل `cn` ونقل tailwind)
- [ ] التأكد إن `api-test.txt` اتمسح من المشروع

لتوليد قيمة عشوائية لأي سر:

```
node -e "console.log(require('crypto').randomBytes(36).toString('base64url'))"
```

## ما تم تأجيله أو تركه

الحاجات دي متغيّرتش عن قصد، وكل واحدة ليها سبب:

| البند | السبب |
| --- | --- |
| الـ 14 جدول اللي مش مستخدمين (مخزون، معامل، تقييمات…) | موجودين في الـ SRS للمراحل الجاية، ومسح جداول مينفعش نرجع فيه |
| مسار الـ SMS | تجهيز مقصود للمزوّد اللي هيتضاف بعدين (قرار D-01) |
| Content-Security-Policy للموقع | Next.js بيحط scripts inline، فالـ CSP محتاج nonces من الـ middleware عشان يتعمل صح |
| الـ migrations القديمة اللي فيها `NOT VALID` و `VALIDATE` في نفس الـ transaction | اتنفذت خلاص. القاعدة من هنا ورايح إنهم يتعملوا في ملفين منفصلين |
| الـ CSS الميت والـ hooks اللي مش مستخدمة | الفايدة قليلة، والأسماء ممكن تكون متركبة وقت التشغيل |
| إجبار reset للحسابات اللي لسه بـ hash قديم | اختياري. الحسابات دي بتتحول لوحدها مع أول دخول |

الحماية اللي بيوفرها role لوحة المنصة بتقفل الطريق من كود العيادات بس. لو حصل injection جوه كود اللوحة نفسها لسه هيوصل للدوال، بس ده كود أصغر بكتير وبيستخدمه الأدمنز بس.
